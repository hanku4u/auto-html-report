# 01 — Overview

## 1. Purpose and scope

`auto_inform` is a Python library that assembles **reports** — single, self-contained HTML files
containing one table with three columns: **Item**, **Data**, **Check**.

Each row of that table is contributed by a **Block**: a small, self-contained class that knows how
to gather one discrete piece of information (a maintenance history from an API, a failing wafer
map, a trend chart) and how to render it as an HTML fragment. The framework guarantees:

- blocks run **concurrently**, each with its own timeout and retry budget;
- a block that fails does **not** take the report down — the failure is rendered into that block's
  cell;
- row order is **deterministic** (the order blocks were supplied);
- the finished document is **self-contained** — inline CSS, images embedded as data URIs, no
  external requests, no JavaScript required.

The library also supports a two-phase workflow for report families that scale with discovered data:

1. **Discovery** — a scheduled job polls APIs for *events* and persists them to an event store.
2. **Processing** — a second, independently scheduled job reads pending events, selects the report
   definition registered for each event *type*, builds the report, and writes it out.

The two phases are deliberately decoupled: they share only the event store, so either can fail,
be re-run, be throttled, or be scheduled on a different cadence without affecting the other. See
[05-discovery-and-processing.md](05-discovery-and-processing.md).

## 2. Non-goals for v1

| Not doing | Why |
| --- | --- |
| Web service / REST API | Reports are generated by scheduled jobs, not served on request. |
| Scheduler / cron implementation | The host CI system owns scheduling. |
| Command-line interface | Deliberate: library-only public surface. See ADR-0001. |
| Interactive JS charts | matplotlib → static PNG data URI. See ADR-0009. |
| PDF or Excel export | HTML only in v1. |
| Publishing to PyPI | Internal tool, installed from git. See ADR-0015. |
| External plugin packages | Blocks are added to this package directly. See ADR-0003. |
| Multi-report-per-file, or a block expanding to multiple rows | One block = one row in v1. See ADR-0011. |
| End-user templating language | Report definitions are Python. See ADR-0016. |
| Localisation / RTL | English, LTR, UTC timestamps only. |

## 3. Glossary

Precision matters here, because "report" is overloaded in ordinary speech. Every document in this
set uses these terms in exactly these senses.

| Term | Meaning | Defined in |
| --- | --- | --- |
| **Block** | A class implementing `Block`. Produces exactly one table row. Splits into a `collect()` phase (I/O) and a `render()` phase (pure). | [02](02-block-authoring.md) |
| **ReportDefinition** | Immutable description of one report: a title plus an ordered sequence of *instantiated* blocks. Pure data; no I/O. | [03](03-report-api.md) |
| **Report** | The assembled result: ordered `ReportRow`s, the run id, and the generation timestamp. Framework data — not yet HTML. | [03](03-report-api.md) |
| **ReportRow** | One row: `item` (Item column), `html` (Data column fragment), and the `BlockOutcome`. | [03](03-report-api.md) |
| **BlockOutcome** | Per-block result: status, duration, attempts, and error summary. | [03](03-report-api.md) |
| **Event** | An immutable value object discovered from an external source: `event_type`, `event_id`, `payload`, `discovered_at`, `source`. | [04](04-events-and-stores.md) |
| **EventStore** | Port that persists events and tracks their lifecycle (`NEW` → `PROCESSED` / `FAILED`). Default: SQLite. Optional: PostgreSQL. | [04](04-events-and-stores.md) |
| **Discoverer** | A class implementing `Discoverer` that produces `Event`s for one `event_type`. | [05](05-discovery-and-processing.md) |
| **ReportFactory** | Callable `(event, context) -> ReportDefinition`. Registered per `event_type`; answers "which blocks, with which parameters, for *this* event?" | [03](03-report-api.md) |
| **Generation** | The act of turning a `ReportDefinition` into assembled `Report` rows (`generate_report`). | [03](03-report-api.md) |
| **Renderer** | Pure function turning a `Report` into an HTML string (`render_report`). | [06](06-output-html.md) |

## 4. Architectural overview

Dependencies point **inwards**. The domain knows nothing about SQLite, S3, Jinja2 or matplotlib;
those live behind ports and are wired at the edge. This is what makes blocks testable without a
network and the framework testable without a bucket.

```
                            ┌──────────────────────────────────────┐
   client code (CI jobs) →  │  public API:  auto_inform/__init__.py │
                            └──────────────────────────────────────┘
                                            │
        ┌───────────────────────────────────┼─────────────────────────────────┐
        ▼                                   ▼                                 ▼
┌────────────────┐              ┌──────────────────────┐          ┌───────────────────┐
│  application   │              │   domain (pure)      │          │  infrastructure   │
│                │  depends on  │                      │  implements ┌───────────────┐ │
│ generate_report│ ───────────► │ Block / Report...    │ ◄─────────── │ SqliteStore   │ │
│ run_discovery  │              │ Event / ExitCode     │  ports       │ PostgresStore │ │
│ run_processing │ ───────────► │ errors               │              │ LocalWriter   │ │
│ collect_blocks │              └──────────────────────┘              │ S3Writer      │ │
└────────────────┘                          ▲                        │ HttpClient    │ │
        │                                   │                        │ settings      │ │
        ▼                        ┌──────────────────────┐            └───────────────┘ │
┌────────────────┐               │  rendering           │                              │
│  registry      │               │  Jinja2 shell, cells │            └───────────────────┘
│  block/report  │               │  figures (matplotlib)│
└────────────────┘               └──────────────────────┘
```

**Rules enforced by `tests/unit/test_layering.py`, module by module.** They were previously "enforced by
review", which is to say not enforced: the failure mode is a stray import written into the wrong file,
and nothing would have noticed.

1. `domain/` imports nothing from `application/`, `infrastructure/` or `rendering/` **at runtime**. One
   deliberate exception exists: `domain/block.py` names `ReportContext` and `RenderContext` in its method
   signatures and imports them under `if TYPE_CHECKING:`. A type annotation creates no runtime
   dependency, and the audit permits *exactly* those two names — a third fails the test, so the exception
   stays bounded and visible rather than accumulating.
2. `application/` may import its own layer, `domain/`, the `Settings` *value* type
   (`infrastructure.settings`), and the shared private helpers at the package root (`_naming`,
   `_version`) — in either the `from auto_inform._naming import slug` or the
   `from auto_inform import _naming` form. Nothing else under `auto_inform` — in particular no concrete
   adapter (`infrastructure.stores`, `infrastructure.writers`, `infrastructure.http_stub`, a real clock)
   and no `rendering`. Those arrive by injection, per rule 3. The audit enforces this as an **allowlist**,
   so a newly added adapter is forbidden by default rather than permitted until somebody remembers to
   extend a tuple; granting a genuine new permission means changing this rule as well as the test.
3. Concrete stores and writers are injected by the caller, or built by a small factory that reads
   `Settings`.
4. `blocks/` and `reports/` import from `domain/`, the rendering helpers, the registry, and the other
   plugin modules they compose (a report family instantiates blocks) — never from `application/` or
   `infrastructure/`. They receive everything they need through `ReportContext` and their own constructor
   parameters.
5. `rendering/` imports `domain/` and the standard library, plus Jinja2 and matplotlib in the modules that
   need them — never `application/` or `infrastructure/`.
6. Modules directly under the package root — `registry.py`, `_naming.py`, `_version.py` — may reach into
   the layers but must never acquire a concrete adapter or the configuration that builds one: their rule
   forbids `infrastructure/`. They were ungoverned until the audit learned to enumerate them, which is how
   `registry.py` could have grown a store dependency with nobody the wiser.

**Type-only imports are not judged.** An annotation under `if TYPE_CHECKING:` is erased at runtime and
creates no dependency, which is the principle behind rule 1's exception. That exception is still
*enumerated* there — the audit asserts the domain's type-only upward set is exactly the two context names
— so it stays visible instead of accumulating. Everywhere else a type-only import is simply not a runtime
dependency, and is not reported.

**The composition root is exempt.** `auto_inform/__init__.py` exists to wire the layers together so that
`from auto_inform import Block` works, and it legitimately imports all of them. One consequence is worth
stating plainly, because an earlier version of rule 1 claimed otherwise: importing *any* module under
this package runs that root first, so `auto_inform.domain.block` cannot be imported "with no application
or infrastructure layer present". What the rule actually guarantees is a fact about the source — the
domain modules do not depend upward — which is what keeps them testable and the dependency arrows
pointing inward.

**And no layer may import that root back.** It imports the layers, so a layer importing it is a cycle.
The audit reports a bare `import auto_inform` in *every* layer, whatever that layer's rule style — under
the denylist rules the bare name matches no forbidden prefix and would otherwise pass silently.

## 5. The two pipelines

```
DISCOVERY JOB  (e.g. every 15 min via CI scheduler)
  Discoverer(s) ──discover()──► [Event, Event, ...] ──store.save()──►  EventStore
       (DiscoveryContext: settings, http, logger, clock)                (NEW rows)

PROCESSING JOB  (e.g. every hour via CI scheduler)
  EventStore.pending(event_type) ──► Event
        │
        ├─ get_report_factory(event_type)(event, context) ──► ReportDefinition
        │        (event-specific parameters are bound here, explicitly, by the factory)
        │
        ├─ generate_report(definition, context)  ── concurrent per-block collect + render
        │        └─► Report (ordered rows, per-block outcomes)
        │
        ├─ render_report(report) ──► HTML string
        │
        ├─ OutputWriter.write(...) ──► local directory or S3
        │
        └─ EventStore.mark_processed(event_id, uri)  |  mark_failed(event_id, reason)
```
